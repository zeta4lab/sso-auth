# 구조

## 한 줄 요약

**토큰 발급은 Ory Hydra가 하고, 이 저장소는 파트너 관리·인가 정책·검증 라이브러리를 맡는다.**

## 왜 이렇게 나누는가

외부 파트너가 붙는 운영 인증 서버를 직접 구현하면 서명 키 관리, 클라이언트 인증,
토큰 재사용 방지, 스펙 준수(RFC 6749·8725·9068)를 전부 직접 책임져야 하고
여기서의 실수는 곧 인증 우회다. 검증된 OAuth2 구현에 그 부분을 맡긴다.

Hydra를 고른 이유는 **사람 로그인 기능이 없는 OAuth2 전용 서버**라서다.
M2M만 다루는 이 프로젝트에 필요 없는 로그인 UI·사용자 저장소가 딸려오지 않는다.
(Keycloak은 그 기능이 기본 포함이라 M2M 전용으로는 과하다. 뒤집을 수 있는 결정이며,
파트너 온보딩을 관리 콘솔로 해결하고 싶어지면 재검토한다.)

이 저장소가 직접 맡는 것은 Hydra가 정책적으로 정해주지 않는 부분이다.

- 파트너 등록과 그에 따른 OAuth2 클라이언트 생성
- 시크릿 무중단 회전과 유출 시 즉시 폐기
- 파트너별 스코프 정책(무엇을 요청할 수 있는가)
- 감사 로그
- 리소스 서버가 쓰는 토큰 검증 라이브러리

## 구성요소

```
파트너 서비스 ──(1) client_credentials──▶ Hydra (토큰 발급)
      │                                      ▲
      │                                      │ Admin API (클라이언트 CRUD)
      │                                (2)   │
      │                            sso-auth 관리 API ◀── 운영자
      │
      └──(3) Bearer 토큰────────────▶ 리소스 서버
                                          │ (4) JWKS로 로컬 검증
                                          ▼
                                    sso-auth 검증 라이브러리
```

1. 파트너는 `client_id`/`client_secret`으로 Hydra의 토큰 엔드포인트에서 액세스 토큰을 받는다.
2. 운영자는 sso-auth 관리 API로 파트너를 등록·회전·폐기한다. Hydra Admin API는 **외부에 노출하지 않는다.**
3. 파트너는 받은 토큰을 `Authorization: Bearer`로 리소스 서버에 제시한다.
4. 리소스 서버는 Hydra의 JWKS로 **로컬 검증**한다. 토큰 서버에 매 요청 묻지 않는다.

## 가용성

액세스 토큰은 비대칭 서명(RS256) JWT이고 리소스 서버는 JWKS를 캐시해 로컬 검증한다.
따라서 **Hydra가 잠시 죽어도 이미 발급된 토큰의 호출은 계속 통과한다.** 그 동안 막히는 것은
새 토큰 발급뿐이며, 토큰 TTL만큼의 유예가 생긴다.

대가는 **즉시 폐기가 안 된다는 것**이다. 폐기한 클라이언트의 토큰도 남은 TTL 동안은 유효하다.
이를 TTL을 짧게 잡아(기본 15분) 감당하고, 즉시 차단이 필요한 사고 상황에서는
리소스 서버가 폐기 목록을 확인하는 경로를 따로 둔다(아래 열린 항목).

## 토큰 형태

- 서명: RS256, Hydra가 보유한 키. 공개키는 JWKS 엔드포인트로 노출.
- `iss`: Hydra 공개 issuer URL
- `sub`: `client_id` (M2M이므로 사용자 주체가 없다)
- `aud`: 호출 대상 API 식별자. 리소스 서버는 **자기 audience가 아니면 거부한다.**
- `scope`: 공백 구분 문자열. 형식은 `<리소스>:<행위>` (예: `reports:read`)
- `exp`: 발급 후 15분 (기본값, 운영 수치는 논의 아젠다 4번)

## 시크릿 회전

파트너 서비스를 멈추지 않고 교체하려면 **두 개의 시크릿이 동시에 유효한 기간**이 필요하다.
Hydra의 클라이언트는 시크릿을 하나만 갖기 때문에, 이 저장소는 파트너 하나에
**클라이언트 두 개(활성/대기)** 를 두는 방식으로 겹침 구간을 만든다.

1. 회전 시작 — 대기 클라이언트에 새 시크릿을 발급하고 파트너에게 전달한다.
2. 겹침 구간 — 옛 시크릿과 새 시크릿이 모두 통한다. 파트너가 전환한다.
3. 회전 완료 — 옛 클라이언트를 폐기한다.

유출 사고 시에는 겹침 없이 즉시 폐기한다(`revoke`).

## 이 저장소가 만들지 않는 것

- 사용자 로그인, 회원가입, 비밀번호 (M2M 범위 밖)
- 자체 토큰 서명·발급 (Hydra가 한다)
- API 게이트웨이 (리소스 서버가 검증 라이브러리를 직접 쓴다)
